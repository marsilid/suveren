# Сверка проверок со стандартами (блок 1b)

Начата 2026-10-22. Здесь записано, где проверка расходилась со стандартом и что
исправлено. Таблица точности по полигону будет добавлена отдельным разделом.

## Почта

| Проверка | Стандарт | Расхождение | Исправление |
|---|---|---|---|
| MTA-STS (SUV-MAIL) | RFC 8461, разд. 3.3 | Файл политики читался с переходом по редиректам, а отправители по ним не переходят: политика за редиректом для них не существует, а Suveren её засчитывал | Политика читается без редиректов (b4ca18a) |
| MTA-STS | RFC 8461, разд. 4.1 | В режиме enforce не сверялись MX-серверы со строками `mx:` политики. Если MX там нет, отправители вроде Gmail на него не доставят письма, а проверка ставила OK | Такой случай теперь FAIL, с названием серверов; шаблон `*.` совпадает ровно с одной меткой (b4ca18a) |
| SPF | RFC 7208, разд. 6.1 | `redirect=` рядом с `all` не применяется, но учитывался в лимите DNS-запросов и проходился | Игнорируется (818214f) |
| SPF | RFC 7208, разд. 5.5 | Механизм `ptr` («SHOULD NOT be used») не отмечался | Предупреждение и совет заменить на `ip4:`/`a:` (818214f) |
| SPF | RFC 7208, разд. 4.6.4 | Лимит 10 DNS-запросов: совпадает | — |
| SPF | RFC 7208, разд. 5.2, 6.1 | include или redirect на домен без единственной SPF-записи ломает всю проверку (permerror), а было WARN | FAIL с объяснением; таймаут DNS остаётся WARN |
| DMARC | RFC 7489, разд. 6.3, 6.6.3 | `p` обязателен, `sp` наследует `p`, несколько записей означают отсутствие DMARC: совпадает. Поиск записи организационного домена не нужен: почта проверяется по зарегистрированному домену | — |
| DMARC | RFC 7489, разд. 6.3, 6.4 | Значение `v` «MUST match precisely», и грамматика задаёт его кодами заглавных букв (`%x44 %x4d…`): `v=dmarc1` по стандарту игнорируется. Suveren принимал любой регистр (сверено с rfc-editor.org 2026-10-23) | Запись по-прежнему читается, но DMARC получает WARN с объяснением; имя тега `V` допустимо |

проверка отзыва сертификата (OCSP/CRL; сделана 2026-10-23: OCSP, а без него — CRL с проверкой подписи). Сделано позже: TXT `_mta-sts` без `id=` или в нескольких экземплярах считается отсутствием политики (RFC 8461, разд. 3.1).

## Полигон: badssl.com, проверка SUV-WEB-008 (TLS)

Прогон 2026-10-22. Ожидание — что скажет браузер или testssl.sh на порту 443.
На badssl.com общий сервер на 443 принимает TLS 1.0 и 1.1 у всех поддоменов,
поэтому WARN за устаревшие протоколы там верен (стенды tls-v1-0/1-1/1-2 на своих
портах 1010–1012 мы не проверяем: Suveren смотрит только 443).

| Стенд | Ожидание | Suveren | Итог |
|---|---|---|---|
| expired | FAIL | FAIL | верно |
| wrong.host | FAIL | FAIL | верно (до исправления: OK) |
| self-signed | FAIL | FAIL | верно (до исправления: OK) |
| untrusted-root | FAIL | FAIL | верно (до исправления: OK) |
| incomplete-chain | WARN | WARN | верно (первая версия исправления давала FAIL: десктопный Chrome сам достраивает цепочку) |
| revoked | FAIL | FAIL | верно с 2026-10-23 (до этого пропуск: отзыв не проверялся). Let's Encrypt с 2025 года не держит OCSP, поэтому отзыв нашёлся по списку отзыва (CRL) |
| mozilla-modern | OK | OK | верно |
| tls-v1-0, tls-v1-1, tls-v1-2, sha256, ecc256 | WARN (TLS 1.0/1.1 на 443) | WARN | верно |

Итого по проблемам сертификата: найдено 6 из 6 (до проверки отзыва — 5 из 6), ложных
срабатываний 0 из 7 исправных сертификатов (точность 100%). До исправлений
было 2 из 6 (только expired и, частично, incomplete-chain как заметка).

## Что поймал ночной прогон по 298 сайтам (2026-10-22)

Первая версия проверки TLS сверяла цепочку с хранилищем Windows. Windows
добавляет корневой сертификат только тогда, когда он впервые нужен, поэтому
новых корней там не было. vk.com (SSL.com TLS RSA Root CA 2022) получил ложный
FAIL, dzen.ru (HARICA TLS ECC Root CA 2021) — ложный WARN. Теперь проверка идёт
по списку корневых сертификатов Mozilla (certifi), как и загрузка страниц через
httpx. Результат одинаков на любой машине, и оба сайта проходят. Если
проверочное соединение не удалось (таймаут), отчёт так и пишет, а не молчит,
будто всё в порядке.

Там же: у positive.com запись SPF — один `redirect` на имя с двумя SPF-записями.
Статус FAIL верный, но текст говорил «нет -all» и советовал про include. Теперь
совет строится по виду проблемы. Самоаудит ловил «опасн» внутри слова
«БЕЗОПАСНАЯ» в названии оператора bi.zone; теперь он ищет начало слова и
пропускает текст в кавычках.
