# Новая проверка в Suveren

Сначала `graphify query "<похожая проверка>"`: найди ближайшую по смыслу существующую
проверку и делай по её образцу (модуль, стиль details/recommendation, тесты).

## 1. Каталог — `src/suveren/catalog.py`
- Добавь `_spec("SUV-<РАЗДЕЛ>-<NNN>", <РАЗДЕЛ>, "<заголовок>", "<модуль>", "<теги>", "<одна строка>")`
  в блок своего раздела. Номер — следующий за последним в разделе; ID никогда не
  переиспользуется и не меняется после выпуска. `-000` зарезервирован под «модуль не запустился».
- Заголовок должен **точно** совпадать с `title` у `Check(...)` в модуле: ID ищется по паре
  (раздел, заголовок). Если заголовок меняется, задай `pattern=True` и регулярное выражение.
  Тесты запускаются с `SUVEREN_STRICT_CHECK_IDS=1`: проверка без записи в каталоге — ошибка.
- `module` — один из `MODULES` (по нему `--checks` решает, какие этапы запускать). Если
  проверке нужны данные нескольких модулей, допиши её ID в `REQUIRES`.
- Теги — существующие (`pd`, `law`, `mail`, `web`, …), новые только при необходимости.

## 2. Код
- `Check(group, title, Status, details, recommendation, law=...)` в модуле раздела.
  Статусы: FAIL — нарушение найдено; WARN — возможная проблема; UNKNOWN — данных не хватило
  (лучше, чем ложная тревога); OK.
- Если модуль новый — подключи его в `scan.py: run_scan` и при необходимости в `advice.py`,
  `scenarios.py`, `templates/report.html.j2`.
- Норма закона или стандарта, на которую опирается вывод, — сверь с текстом источника
  (RFC, OWASP, 152-ФЗ, КоАП) до написания, а не после.

## 3. Полигон — `tests/lab.py`
- Ожидание записывается **до** запуска: что ответил бы внимательный аудитор по стандарту.
- Добавь `Case("lab-<имя>", "<что сломано>", {"SUV-...": "fail"}, html=..., headers=..., files=...)`
  на каждый значимый исход (fail/warn/ok) и, если проверка смотрит на хороший сайт,
  ID с `"ok"` в `lab-good`.
- Расхождение с ожиданием не «подгоняй»: либо исправь проверку, либо внеси в `KNOWN` с причиной.

## 4. Тесты модуля — `tests/test_<модуль>.py`
Юнит-тесты на разбор и пограничные случаи. Всё офлайн: httpx `MockTransport`, фейковые DNS и TLS
(образцы — в `tests/lab.py` и `tests/test_e2e.py`). Покрытие не ниже 90%.

## 5. Документация
- `docs/checks.md` генерируется, руками не править:
  `PYTHONUTF8=1 .venv/Scripts/python -m suveren checks --markdown > docs/checks.md`
  (`test_docs_checks_md_is_up_to_date` сверяет файл с каталогом).
- Таблицу полигона в `docs/accuracy.md` обнови выводом `python tests/lab.py --markdown`
  и поправь число сайтов в тексте.
- Проверки по страницам сайта (152-ФЗ, согласие, вход через иностранные сервисы): прогони
  `tests/test_corpus.py`; если вывод поменялся сознательно — `python tests/golden.py update`.

## 6. Проверка и коммиты
- `.venv/Scripts/python tools/ci.py` — всё должно быть зелёным.
- Коммит кода: короткая английская фраза о сути, ID в конце —
  `Compare the privacy policy with what the site does (SUV-PD-011)`.
- Отдельным коммитом `CHANGELOG: <о чём>` — запись по-русски в «## Не выпущено»: что теперь
  находит проверка и на каком основании (статья закона, раздел RFC), с примером сайта, если есть.
